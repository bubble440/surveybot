[P1 — CRITIQUE] TCP/IP Stack fingerprint (TTL, Window Size, JA4T)
    Statut : NON VÉRIFIÉ EN PROD — à corriger en priorité absolue
    Hypothèse : le TCP/IP stack de Linux (Fly.io) trahit l'OS réel indépendamment
    de tout spoofing Chrome/CDP. Ces valeurs sont fixées par le kernel.
    Valeurs attach (référence Windows) :
      - JA4T         : 65535_2-1-3-1-1-4_1460_8
      - Satori       : 65535:128:1:52:M1460,N,W8,N,N,S:.
      - Satori Sig   : Windows 8
      - Initial TTL  : 128 (Windows default)
      - Window Size  : 65535
      - MSS Value    : 1460
      - Window Scale : 8 (×256)
      - TCP Options  : MSS, NOP, WINDOW, NOP, NOP, SACK_PERM
      - Zardaxt      : Windows 54%
    Valeurs attendues en prod Linux non patchée :
      - Initial TTL  : 64 → trahit Linux immédiatement
      - Window Size  : 14600 ou 29200 → divergence forte
      - Satori Sig   : Linux
      - Zardaxt      : Linux >80%
    Correction envisagée :
      - TTL : sysctl net.ipv4.ip_default_ttl=128 (faisable sur Fly.io)
      - Window Size : tuning kernel TCP (net.ipv4.tcp_rmem / tcp_wmem)
      - MSS : lié au MTU, probablement déjà 1460 ✅
    Note : impossible à spoofer via CDP ou JavaScript — niveau kernel uniquement.

[P2 — CRITIQUE] Client Hints HTTP (sec-ch-ua-platform, platformVersion)
    Statut : NON VÉRIFIÉ EN PROD — divergence quasi-certaine
    Hypothèse : Chrome envoie sec-ch-ua-platform="Linux" dans chaque requête HTTP
    en prod, alors que le UA spoofé indique Windows. Cette incohérence est triviale
    à détecter pour tout anti-bot.
    Valeurs attach (référence) :
      - sec-ch-ua-platform : "Windows"
      - platformVersion    : 19.0.0
      - architecture       : x86
      - bitness            : 64
      - wow64              : false
      - mobile             : false
      - formFactors        : ["Desktop"]
      - uaFullVersion      : 149.0.7827.103
      - fullVersionList    : Google Chrome 149.0.7827.103, Chromium 149.0.7827.103,
                             Not)A;Brand 24.0.0.0
      - brands             : Google Chrome 149, Chromium 149, Not)A;Brand 24
    Distinction Low Entropy (envoyés automatiquement sur chaque requête) :
      - sec-ch-ua, sec-ch-ua-mobile, sec-ch-ua-platform → toujours envoyés
    Distinction High Entropy (envoyés sur demande serveur via Accept-CH) :
      - platformVersion, architecture, bitness, wow64, uaFullVersion, fullVersionList
    Correction envisagée :
      - Emulation.setUserAgentOverride avec userAgentMetadata complet incluant
        platformVersion, architecture, bitness, wow64, model, platform.
      - Vérifier que sec-ch-ua-platform est bien "Windows" dans HTTP/2 frames.

[P3 — HAUTE] WebRTC IP leak
    Statut : NON VÉRIFIÉ EN PROD
    Hypothèse : WebRTC expose l'IP réelle de la machine Fly.io en plus de l'IP proxy.
    Valeurs attach (référence — propre) :
      - WebRTC Leak Test  : No Leak
      - Local IP Address  : - (aucune IP locale exposée)
      - Public IP (WebRTC): 176.186.86.39 (= IP proxy, cohérent)
      - SDP Log           : IN IP4 127.0.0.1 uniquement
    En prod, risque que le SDP expose l'IP interne Fly.io (fdaa::/7 ou 172.x.x.x)
    ou l'IP publique CDG Fly.io à côté de l'IP proxy.
    Correction envisagée : désactiver WebRTC via CDP ou flag Chrome.

[P4 — HAUTE] DNS leak
    Statut : NON VÉRIFIÉ EN PROD
    Hypothèse : Chrome résout les DNS via les resolvers Fly.io/Cloudflare au lieu
    des DNS du proxy IPRoyal, créant une incohérence IP/DNS détectable.
    Valeurs attach (référence — propre) :
      - IP visible    : 176.186.86.39 (proxy IPRoyal)
      - ISP visible   : BOUYGUES Telecom, France Paris
      - DNS Server 1  : 89.85.114.32 — Bouygues Telecom ISP — France, Paris
      - DNS Server 2  : 2001:860:de02::4 — Bouygues Telecom ISP Wireline — France, Paris
    En prod, risque que les DNS resolvent via Fly.io (fdaa::3) ou Cloudflare (1.1.1.1)
    pendant que l'IP de sortie reste IPRoyal → discordance ISP/DNS flagrante.
    Correction envisagée : forcer les DNS via le proxy dans la config Chrome/réseau.

[P5 — HAUTE] TLS fingerprint (JA3/JA4) — impact proxy

      - JA4_o  : t13d1516h2_ac8d58a92679_73abcacf8021

      - JA3_n  : 8e19337e7524d2573be54ef820784c9
      - Cipher : TLS_AES_128_GCM_SHA256
      - Key Ex : X25519MLKEM768 (post-quantique hybride)

      - Device Orientation   : true en attach → probablement false en prod

    La Battery API est la plus connue comme signal headless/VM.
