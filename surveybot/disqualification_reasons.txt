================================================================================
PRINCIPE FONDAMENTAL — À LIRE AVANT TOUTE INVESTIGATION
================================================================================

Le mode local (attach, Windows, Chrome headed, GPU physique) ne sert QUE de
référence de spoofing. Les SDK anti-bot (DataDome, PerimeterX, etc.) n'ont
AUCUN accès au mode local et ne peuvent donc PAS comparer prod vs local.

Toute piste formulée comme "le fingerprint diffère entre prod et local"
est invalide comme explication du blocage. La question correcte est toujours :
"Est-ce que le fingerprint PROD correspond à un profil légitime connu ?"

Le local sert uniquement à établir une cible de spoofing crédible (Chrome 149
Windows NT 10.0). C'est tout.

================================================================================
BILAN — SITUATION AU 2026-06-17
================================================================================

Tous les vecteurs mesurables ont été testés et éliminés :
  - Réseau      : IP, DNS, TLS, HTTP/2, peetprint → identiques ou non causaux
  - Browser JS  : navigator.*, WebGL, Canvas, fonts, WebRTC → identiques ou corrigés
  - Infrastructure : CDP, profil Chrome, cookies, timing, referrer → éliminés

Le blocage Cint ("Verification Required — bot activity on IP X.X.X.X") persiste.

HYPOTHÈSE RESTANTE LA PLUS PROBABLE :
Le signal de détection n'est pas dans le fingerprint statique mais dans le
comportement dynamique de Chrome au moment de la connexion. Candidats :

  a) Absence d'historique de navigation dans le profil vierge
     Chrome réel accumule des cookies tiers, cache, historique — un profil
     100% vierge est statistiquement anormal et potentiellement détecté
     comme tel par DataDome via les headers Cache-Control / ETag / cookies
     tiers attendus.

  b) Comportement scroll/mouse inexistant avant le premier driver.get()
     DataDome peut scorer l'absence totale d'événements souris/scroll
     avant la première requête comme signal bot fort.

  c) Ordre ou contenu des headers HTTP non standard
     Accept, Accept-Encoding, Accept-Language, Cache-Control — à vérifier
     via un proxy d'interception (mitmproxy) entre Chrome prod et Cint.
